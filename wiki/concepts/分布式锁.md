# 分布式锁

在分布式系统中，跨 JVM 进程的互斥访问控制机制。解决多台机器上多个服务并发访问共享资源时的竞态问题（如超卖、重复插入）。

## 分布式锁的四大条件
1. **互斥性**：同一时刻只有一个客户端持有锁
2. **无死锁**：持锁方崩溃后锁能自动释放（超时机制）
3. **容错性**：大多数节点正常即可运作
4. **解铃还须系铃人**：只有加锁方能解锁（避免误解他人的锁）

## 主要实现方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 数据库悲观锁（FOR UPDATE） | 简单可靠 | 高并发性能差 |
| 数据库乐观锁（CAS + version） | 无阻塞 | ABA 问题；高并发大量重试 |
| ZooKeeper | 可靠性高 | 性能低于 Redis |
| **Redis** | 高性能 | 需处理原子性与续期 |

## Redis 分布式锁实现

### 基础：SET NX PX（原子加锁）
```redis
SET lock_key unique_value NX PX 30000
```
- `NX`：Key 不存在才设置（互斥）
- `PX 30000`：30 秒自动过期（防死锁）
- `unique_value`：每个客户端唯一值（防止解他人的锁）

### 解锁：Lua 脚本保证原子性
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### Redisson（推荐生产使用）
Java 客户端，提供开箱即用的分布式锁：
- **WatchDog 自动续期**：锁持有期间每 10s 自动将 TTL 续到 30s，防止业务未完成锁已过期
- **可重入锁**：同一线程可多次加锁
- **读写锁**：读读不互斥，读写/写写互斥
- **公平锁**：FIFO 顺序获取

### RedLock 算法（多节点容错）
向 N 个独立 Redis 节点加锁，超过 N/2+1 个成功才视为加锁成功。防止单点故障。

## 与本地锁对比
| | 本地锁（synchronized/ReentrantLock） | 分布式锁 |
|--|------|------|
| 作用范围 | 单 JVM 进程内 | 跨进程/跨机器 |
| 实现 | JVM 内置 | Redis/ZK/DB |
| 性能 | 极高 | 有网络开销 |
