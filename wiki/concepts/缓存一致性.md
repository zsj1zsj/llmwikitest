# 缓存一致性

缓存与主数据库（如 MySQL）之间的数据同步问题，是分布式系统的核心挑战之一。使用缓存本身即意味着放弃强一致性换取性能——缓存系统属于 CAP 中的 AP，只能实现**最终一致性**。

## 四种缓存读写策略

### Cache-Aside（旁路缓存）——最常用
- **读**：先查缓存，命中返回；未命中查 DB，将结果写入缓存再返回
- **写最佳实践**：先写 DB，再**删除**缓存（而非更新缓存）
- 删除而非更新的原因：更新缓存在高并发下有竞态问题；删除简单且副作用仅是增加一次 cache miss

### Read-Through
缓存未命中时，由缓存层自动从 DB 加载写入，应用只与缓存交互。关注点分离，代码整洁。

### Write-Through（写穿）
写请求先更新缓存，缓存**同步**更新 DB。应用无需处理故障重试，但写延迟高。与 Read-Through 配合最佳。

### Write-Behind（写后/异步写）
写请求只更新缓存，DB 更新**异步**进行。写性能最高，但一致性最弱，不适合强一致场景。

## Cache-Aside 写操作四种顺序对比

| 顺序 | 核心风险 | 是否推荐 |
|------|----------|----------|
| 先更新缓存，再更新 DB | DB 失败 → 缓存为脏数据 | ✗ |
| 先更新 DB，再更新缓存 | 并发写竞态 → 缓存值错误 | ✗ |
| 先删缓存，再更新 DB | 读请求回填旧值 | ✗ |
| **先更新 DB，再删缓存** | 极端情况短暂不一致 | ✓ 推荐 |

## 延迟双删（Delay Double Delete）
在"先更新 DB，再删缓存"基础上，延迟 500ms 再次删除缓存，消除两步之间读请求写入旧值的窗口。

```
1. 删缓存
2. 更新 DB
3. sleep ~500ms
4. 再次删缓存
```

## 删除失败的保障
- **MQ 异步重试**：删除失败发送消息到消息队列，异步重试，不侵入业务代码
- **订阅 bin-log（Canal）**：监听 MySQL binlog 变更，异步删除对应缓存，彻底解耦
