### redis 数据类型有哪些？
#### **字符串（String）：**
    - **描述：** 最基本的数据类型，可以存储文本、数字或二进制数据。
    - **示例：** 存储用户的姓名、年龄等信息。
#### **列表（List）：**
    - **描述：** 有序的字符串集合，支持在两端推入或弹出元素。
    - **示例：** 实现消息队列或任务列表。
#### **集合（Set）：**
    - **描述：** 无序的字符串集合，元素唯一，不支持重复。
    - **示例：** 存储标签、兴趣爱好等信息。
#### **有序集合（Sorted Set）：** 
    - **描述：** 类似于集合，但每个元素都有一个关联的分数（score），元素按分数排序。
    - **示例：** 实现排行榜、优先级队列等功能。

#### **哈希（Hash）：**
    - **描述：** 键值对集合，适合存储对象类型的数据。
    - **示例：** 存储用户信息，如用户名、密码、邮箱等字段。
      购物车：在电子商务应用中，使用哈希表存储用户的购物车信息，其中字段可以是商品 ID，值为商品数量。
- **位图（Bitmap）：**
    - **描述：** 对字符串的每个比特位进行操作，适合进行大规模的布尔值存储。
    - **示例：** 统计用户活跃情况、签到记录等。
- **HyperLogLog：**
    - **描述：** 用于估算集合基数（即集合中不同元素的数量）的概率性数据结构，占用内存少，适合大规模数据统计。
      **适用于量特别大，但是对精度要求不高的**
    - **示例：** 统计网站的独立访客数量。
- **流（Stream）：**
    - **描述：** 用于存储消息队列数据，支持消费者组，适合处理实时数据流。
    - **示例：** 实时日志处理、事件溯源等。
- **地理空间（Geospatial）：**
    - **描述：** 用于存储地理空间数据，支持范围查询和距离计算。
    - **示例：** 存储商铺位置，查询附近的商铺。

### redis如何创建集群？
- **准备环境：**
    - 确保您有多台服务器或虚拟机，每台上都安装了 Redis。
    - 为每个 Redis 实例配置不同的端口，例如 7000、7001、7002 等。

- **配置 Redis 实例：**
    - 编辑每个 Redis 实例的配置文件（通常位于 `redis.conf`），进行以下修改：
        - 设置 `daemonize` 为 `yes`，使 Redis 以守护进程方式运行。
        - 设置 `port` 为实例监听的端口号。
        - 启用集群模式：`cluster-enabled yes`。
        - 指定集群配置文件：`cluster-config-file nodes-<port>.conf`。
        - 设置集群节点超时时间：`cluster-node-timeout 15000`。
        - 关闭保护模式：`protected-mode no`。
    - 确保每个实例的配置文件在同一目录下，便于管理。

- **启动 Redis 实例：**    
    - 在每台服务器上，使用修改后的配置文件启动 Redis 实例。

- **创建集群：**
    - 在任意一台机器上，使用 `redis-cli` 工具创建集群。
    - 执行以下命令，其中替换 `<password>` 为您的密码（如果设置了密码），并列出所有 Redis 实例的 IP:PORT：
        
        `./redis-cli -a <password> --cluster create \ 192.168.100.101:7000 192.168.100.101:7001 192.168.100.101:7002 \ 192.168.100.102:7000 192.168.100.102:7001 192.168.100.102:7002 \ --cluster-replicas 1`
        
        - `--cluster-replicas 1` 参数表示每个主节点有一个从节点。
        - 系统会提示您确认集群配置，输入 `yes` 即可。
- **验证集群状态：**
    - 使用以下命令连接到集群中的任意节点：
        `./redis-cli -a <password> -c -p 7000`
    - 执行 `cluster info` 查看集群状态，确保显示 `cluster_state:ok`。

### redis是单线程还是多线程？
Redis 是 **单线程** 的。也就是说，Redis 在处理所有的客户端请求时，只有一个线程在执行。这包括读取数据、处理写操作、执行命令等。

#### 单线程凭什么保证性能？

尽管 Redis 是单线程的，但它依然能在高并发场景下保持良好的性能，这主要归功于以下几个因素：

##### 1. **I/O 多路复用（非阻塞 I/O）**

Redis 使用了 **I/O 多路复用** 技术来处理客户端的请求。它通过单线程事件循环来管理多个客户端连接，而不是为每个连接分配一个线程。这意味着，Redis 可以在一个线程内同时处理多个客户端请求，避免了线程切换和上下文切换的开销。

在实际操作中，当 Redis 接收到客户端请求时，它并不会阻塞等待某个操作的完成，而是通过非阻塞方式处理 I/O 操作，允许它快速响应其他请求。

##### 2. **快速的内存操作**
Redis 主要存储数据在内存中，内存的读写速度极快。相比于磁盘操作，内存读写的延迟非常低。这使得即使是单线程执行操作，Redis 也能保持很高的性能。

所有的 Redis 数据操作都是直接操作内存数据结构，且 Redis 内部使用非常高效的算法和数据结构（如**哈希表、跳表**等），这些数据结构提供了非常快速的查找和更新操作。

##### 3. **命令执行的原子性**
Redis 每次处理一个命令时，都会将整个命令的执行过程看作一个原子操作。这个操作要么完全成功，要么完全失败。由于 Redis 是单线程的，避免了多线程环境下常见的并发问题（如竞争条件和锁），减少了同步和上下文切换的开销。

##### 4. **避免了上下文切换的开销**
多线程编程在高并发的情况下需要进行线程上下文切换，而线程的切换是非常耗时的，特别是当线程数较多时。而 Redis 只用一个线程来处理所有请求，避免了多线程并发时频繁上下文切换的开销。

##### 5. **CPU 利用率高**
由于 Redis 是单线程的，它的 CPU 利用率通常会接近 100%（单核）。在多核机器上，虽然只有一个线程执行，但是因为大部分操作都在内存中完成，Redis 仍然能高效地处理大量的请求。如果需要更高的并发性能，Redis 可以通过 **分布式部署** 来横向扩展，利用多台机器来分担负载。

##### 6. **事件驱动模型**
event loop
Redis 使用 **事件驱动模型** 来处理所有的请求和响应。事件驱动模型允许 Redis 在同一个线程内有效地管理多个客户端的连接。当一个客户端的请求完成时，Redis 会立即继续处理下一个请求，而不需要等待和其他请求的冲突或同步。因此，Redis 的效率非常高，尤其是在大量短小请求的情况下。

#### 总结
Redis 的单线程模型通过高效的内存操作、非阻塞 I/O、多路复用、原子命令执行等技术，能够在高并发情况下仍然保持较高的性能。虽然 Redis 是单线程的，但它的设计非常高效，避免了多线程带来的上下文切换和同步问题，同时利用内存的高效存取和事件驱动模型，保证了其在性能上的优势。

### redis 的分布式部署 如何确保用户查找的数据在他访问的 redis 上？

在 Redis 的分布式部署中，**确保用户查找的数据在访问的 Redis 节点上**是通过 **数据分片（Sharding）** 来实现的。Redis 使用 **集群模式** 来管理数据的分布，数据被分散存储在多个 Redis 实例中（即多个节点），每个节点保存一部分数据。通过一些机制，Redis 能确保用户访问到的数据是正确的，即数据被存储和查找的节点是正确的。

### Redis 集群的分片机制

Redis 集群通过 **哈希槽（Hash Slots）** 和 **一致性哈希** 来确保数据分布和高效访问。

1. **哈希槽（Hash Slots）**
    - Redis 集群将数据划分为 **16384 个哈希槽**（这个数字是固定的，不能更改）。
    - 每个键（Key）在写入 Redis 时会经过哈希计算，Redis 使用 **CRC16** 算法对键进行哈希计算，并将哈希值映射到 16384 个哈希槽中的一个。
    - 这些哈希槽会均匀分配到 Redis 集群中的各个节点。每个节点负责一部分哈希槽，也就是负责一部分数据。
2. **数据分布**
    
    - 每个 Redis 节点负责处理一定数量的哈希槽。例如，假设 Redis 集群中有 3 个节点，那么这些节点会负责将哈希槽的 16384 个槽分配到它们之间。
    - 假设每个节点负责 5461 个哈希槽（16384 ÷ 3），节点负责的数据会在它所负责的哈希槽中。
3. **数据访问**
    
    - 当客户端请求某个键时，Redis 会计算该键的哈希槽，并根据哈希槽的值找到对应的节点。如果该键对应的哈希槽存在于该节点上，节点直接返回数据。
    - 如果请求的数据在另一个节点上（即该节点不负责该哈希槽），Redis 会返回一个 **MOVED** 错误，指示客户端去正确的节点请求数据。客户端会根据返回的信息去访问正确的节点。
4. **一致性哈希和槽迁移**
    
    - 在 Redis 集群中，当节点被添加或删除时，哈希槽会进行迁移和重新分配。这是为了确保数据能够均匀地分布到所有节点上，并保持负载均衡。
    - Redis 集群的设计使得 **节点扩展性** 得到了保证，节点数增加时，哈希槽的迁移是透明的，客户端能够感知到的唯一变化是它们会访问不同的 Redis 节点。

#### 具体示例
假设我们有一个 Redis 集群，其中有 3 个节点，负责 16384 个哈希槽。每个节点负责 5461 个哈希槽。

1. **键的存储：**
    
    - 假设我们有一个键 `user:1000`，Redis 会使用 CRC16 算法计算该键的哈希值，然后通过该哈希值计算出对应的哈希槽（例如，哈希值可能指向哈希槽 2000）。
    - 该哈希槽可能分配给 `192.168.1.1:6379` 这个 Redis 节点，因此，`user:1000` 会存储在该节点上。
2. **客户端访问：**
    
    - 当客户端请求 `GET user:1000` 时，Redis 会计算出 `user:1000` 对应的哈希槽（假设是 2000）。然后它会检查该哈希槽归哪个节点管理。
    - 如果该哈希槽归 `192.168.1.1:6379` 管理，客户端会直接从该节点获取数据。
    - 如果该哈希槽归其他节点管理，Redis 会返回一个 `MOVED` 错误，指示客户端去正确的节点（例如 `192.168.1.2:6379`）请求数据。

### 高可用和故障恢复
- **主从复制：** Redis 集群支持主从复制机制。每个主节点都有一个或多个从节点作为备份。如果某个主节点宕机，集群会自动提升某个从节点为新的主节点，保证数据的高可用性。
- **故障转移：** 当某个节点失败时，Redis 集群会自动进行故障转移。集群会重新调整哈希槽的分配，以确保集群中仍然有足够的主节点可以处理请求。
#### 总结

Redis 集群通过 **哈希槽** 和 **数据分片** 的方式将数据分布到不同的节点上。每个键对应一个哈希槽，客户端通过哈希槽找到对应的节点，从而实现数据的分布和访问。即使集群中某个节点宕机或发生故障，Redis 也能通过主从复制和故障转移机制，保证数据的高可用性和一致性。
